# Архитектура веб-приложения «Ориентир»

> Статус: черновик, версия для учебного прототипа (путь C). Основа: `analysis.md`, `problem.md`, `functional.md`.
> Графическая схема: `architecture.excalidraw`. Решения, которых нет в исходных документах и которые предложены как проектные, помечены словом «предлагается» или вынесены в раздел «Открытые вопросы».

## 1. Цели и ограничения

**Что должна обеспечить архитектура:**
- сверку введённых показателей с референсными интервалами и пометку отклонений;
- справочные пояснения и рекомендации врачу по правилам справочника;
- полное отсутствие обработки и хранения персональных данных.

**Ограничения:**
- Прототип нужно сдать к 1 декабря.
- Размещение в Yandex Cloud.
- Для оформления текста используется YandexGPT.
- Прототип работает на вымышленных данных, рекомендации основаны на учебных правилах и помечены как не для клинического применения.
- Сервис не ставит диагноз, не назначает лечение и не делает выводов по сочетанию показателей.

## 2. Общий обзор

«Ориентир» — клиент-серверное веб-приложение без хранения данных пациента. Врач работает в браузере с формой ввода. Backend проверяет ввод, считает отклонения, находит в справочнике пояснения и сработавшие правила рекомендаций и при необходимости обращается к YandexGPT, чтобы оформить текст. Введённые данные существуют только в памяти во время обработки запроса и в ответе, который видит врач.

Цепочка: **Врач → Frontend → Backend (Django) → PostgreSQL (справочник и правила) / YandexGPT**.

Frontend и Backend разделены логически, физически на старте это одно Django-приложение (раздел 9).

## 3. Роли

| Роль | Кто | Что делает | Интерфейс |
|---|---|---|---|
| Врач | Сотрудник ДРКБ (в прототипе — демонстрация) | Вводит возраст, пол, показатели, значения и интервалы, читает результат и рекомендации | Форма и страница результата |
| Администратор | Команда проекта | Ведёт справочник, правила рекомендаций и правила для ИИ | Админ-панель |
| Медицинский эксперт | Специалист ДРКБ | Утверждает пояснения и правила (этап внедрения) | Вне системы или через админ-панель |

## 4. Компоненты

### 4.1 Frontend (веб-интерфейс)
- **Форма врача:** возраст (годы и месяцы), пол, выбор показателя из списка, значение, нижняя и верхняя границы интервала. Свободного текста нет. Поле можно добавить для нескольких показателей сразу. Доступны демонстрационные сценарии одной кнопкой.
- **Страница результата:** список показателей со статусом (ниже, в пределах, выше), величиной отклонения и полосой, показывающей положение значения относительно интервала (предлагается: простая полоса на HTML и CSS). Для отклонённых показателей справочное пояснение и рекомендация для рассмотрения, если сработало правило.
- **Пометки:** на каждой странице заметная надпись «Учебный прототип: не для клинического применения»; рядом с рекомендациями «Рекомендация для рассмотрения врачом».
- **Админ-панель:** справочник показателей, правила рекомендаций, правила для ИИ.

### 4.2 Backend (Django)

| Модуль | Ответственность |
|---|---|
| Проверка ввода | Допускает только числа и значения из списков, проверяет диапазоны (возраст 0–18 лет, нижняя граница меньше верхней), отклоняет всё остальное |
| Расчёт отклонений | Сравнивает значение с интервалом и вычисляет величину отклонения. Обычный код, без ИИ |
| Справочник показателей | Выдаёт название, синонимы, единицу измерения и справочное пояснение |
| Модуль рекомендаций | По показателю, направлению отклонения, возрасту и полу выбирает правило из справочника. Работает локально в коде, возраст и пол наружу не передаются |
| ИИ-модуль | Формирует запрос к YandexGPT, применяет запреты, проверяет ответ, при проблеме возвращает текст из справочника в исходном виде |
| Администрирование | Ведение справочника, правил рекомендаций и правил для ИИ |

Backend не записывает введённые врачом данные ни в базу, ни в файлы, ни в журналы.

### 4.3 База данных (PostgreSQL)
Хранит только служебные данные, никаких данных пациента:
- **Справочник показателей:** названия, синонимы, единицы измерения, справочные пояснения.
- **Правила рекомендаций:** показатель, направление отклонения, при необходимости возрастная группа и пол, текст, тип рекомендации, статус («учебное» или «утверждено»).
- **Правила для ИИ:** запреты и требования к тексту.
- **Демонстрационные сценарии:** вымышленные наборы значений.
- **Учётные записи администраторов.**

### 4.4 YandexGPT
Внешний сервис, вызывается по HTTPS API из ИИ-модуля Backend. Получает название показателя, направление отклонения (ниже или выше) и текст сработавшего правила, без значений, возраста и пола. Задача: оформить пояснение и рекомендацию в связный текст, не добавляя новых фактов и рекомендаций. Frontend напрямую с YandexGPT не общается.

## 5. Ключевые потоки

### 5.1 Оценка анализа (сценарий 1)
1. Врач вводит возраст, пол и для каждого показателя значение и интервал из бланка.
2. Backend проверяет ввод. При ошибке возвращает понятное сообщение, и на этом обработка заканчивается.
3. Расчётный модуль определяет статус каждого показателя и величину отклонения.
4. Для отклонённых показателей Backend берёт из справочника пояснение, а модуль рекомендаций ищет сработавшее правило. Если правила нет, рекомендация не выдаётся.
5. ИИ-модуль отправляет в YandexGPT название показателя, направление отклонения и тексты пояснения и правила вместе с запретами, получает оформленный текст.
6. Ответ проверяется на соответствие правилам (раздел 6). Если он нарушает запреты, пуст или сервис недоступен, используются тексты из справочника в исходном виде.
7. Врач видит результат с пометками. Данные нигде не сохраняются.

### 5.2 Демонстрация (сценарий 7)
1. Врач (на защите — докладчик) выбирает демонстрационный сценарий.
2. Backend подставляет вымышленные значения и выполняет шаги 3–7 потока 5.1.

### 5.3 Администрирование (сценарий 6)
1. Администратор входит в админ-панель.
2. Добавляет и изменяет показатели, пояснения, правила рекомендаций и правила для ИИ.
3. Изменения учитываются при следующих запросах.

## 6. Ограничения ИИ и их реализация

Запреты из `problem.md` и `functional.md`: нет диагноза, нет лечения и препаратов, нет рекомендаций вне правил, нет выводов по сочетанию показателей. Предлагается обеспечивать их несколькими уровнями:
- **Минимум данных для ИИ:** модель получает название показателя, направление отклонения и текст правила. Данных о ребёнке у неё нет.
- **Рекомендации из правил, а не из модели:** факт рекомендации определяет правило справочника. ИИ только оформляет текст и ничего не добавляет.
- **Инструкции модели:** запреты прописываются в системных инструкциях.
- **Проверка ответа:** Backend сверяет текст с правилом: в нём допустимы только типы рекомендаций и специалисты, названные в правиле; ищет запретные темы (диагнозы, препараты, схемы лечения). При нарушении ответ отбрасывается.
- **Запасной вариант:** при отбраковке или недоступности ИИ показывается текст правила из справочника.
- **Пометки:** рядом с рекомендациями указано, что это рекомендации для рассмотрения врачом; на страницах пометка об учебном прототипе.
- **Статус правил:** правила без отметки «утверждено» показываются как учебные.

## 7. Персональные данные и безопасность

**Принципы:**
- **Минимизация.** В форме нет полей для имени, номера карты, дат и свободного текста. Возраст указывается в годах и месяцах.
- **Нет хранения.** Введённое не пишется в базу, файлы и журналы. Технические журналы содержат только время, адрес страницы и код ответа, без тела запросов.
- **ИИ без идентификаторов.** В YandexGPT не уходят значения, возраст и пол.
- **Защита от злоупотреблений.** Ограничение частоты запросов, чтобы нельзя было перегружать сервис и расходовать ИИ-квоту (предлагается).
- **Защита каналов.** HTTPS, ключи доступа к YandexGPT хранятся в секретах, а не в коде.
- **Содержимое справочника.** В реальной эксплуатации пояснения и правила проходят утверждение медицинским экспертом.

**Что нужно проверить:** отключается ли логирование запросов к YandexGPT на стороне Yandex Cloud, и допустимо ли использовать внешний ИИ-сервис по правилам больницы.

## 8. Развёртывание

- Приложение и PostgreSQL размещаются в Yandex Cloud.
- YandexGPT подключается как внешний сервис по API.
- Конкретные сервисы Yandex Cloud выбираются на этапе реализации.
- Для прототипа достаточно одного окружения.

## 9. Технологии (предлагается)

Выбор сделан под первый проект и срок до 1 декабря: как можно меньше разных частей и как можно больше готового.

| Часть | Выбор | Почему |
|---|---|---|
| Язык и фреймворк | Python + Django | Один язык и одна кодовая база, готовая проверка форм и админка |
| Админ-панель | Встроенная админка Django | Закрывает ведение справочника, правил рекомендаций и правил для ИИ без отдельной разработки |
| Frontend | Страницы Django (шаблоны) и немного JavaScript | Не нужны отдельное приложение и отдельный API |
| База данных | PostgreSQL | Нужна для справочника, правил и настроек |
| ИИ | YandexGPT по API | По заданию |
| Развёртывание | Docker-контейнер в Yandex Cloud | Одинаковая среда у разработчика и на сервере |

## 10. Открытые вопросы

1. **Допустимость формата прототипа.** Подтвердить у руководителя задания, что учебный прототип на вымышленных данных с учебными правилами допустим и не требует регистрации как медицинское изделие (предположение, не проверено).
2. **Источник учебных правил.** Откуда взять примеры правил рекомендаций: от руководителя, от эксперта ДРКБ или из открытых методических материалов. Придумывать клинические нормы самостоятельно не следует.
3. **Статус медицинского изделия при внедрении.** Заключение больницы и юриста, нужно ли регистрировать программу с рекомендациями.
4. **Внешний ИИ-сервис.** Допустимо ли отправлять название показателя, направление отклонения и текст правила в YandexGPT, или ИИ должен работать внутри контура больницы.
5. **Доступ врачей при внедрении.** Варианты: без входа, но из внутренней сети больницы; общий ключ; личные учётные записи. Личные учётки означают хранение персональных данных врачей.
6. **Какие показатели в прототипе.** Предлагается небольшой набор, например несколько показателей общего анализа крови, для которых есть учебные правила.
7. **Срок контроля в рекомендациях.** Берётся из правила. Нужен ли вообще срок в прототипе или достаточно формулировки «рассмотреть контроль».
8. **Логирование YandexGPT.** Можно ли отключить на стороне сервиса.
9. **Единицы измерения.** В разных лабораториях они могут отличаться. В прототипе единица фиксирована для каждого показателя, нужен ли перевод.
10. **Размещение.** Есть ли требования больницы к хостингу и доступу.
